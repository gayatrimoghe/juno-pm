## What Juno Is Doing

Insight synthesis — Juno pulls a week of scattered customer feedback out of Slack, Jira, Notion, the support queue and the CRM, and turns it into one Monday 8am digest: five themes, how many separate customers raised each, the verbatim quote, the P0–P3 priority looked up against the strategy framework, and whether the theme is already committed on the roadmap.

## Four Levers

**Stop Conditions** (Loop):

max_steps: 12 tool calls. At 12 it ships what it has labelled “turn limit reached, counts are incomplete.” No quiet truncating.

Early abort, any one of: same tool fails twice in a row (~5 min apart) → drop that source, name it in the window line, keep going. read_framework, read_roadmap or read_capacity_note fails twice → whole run aborts, no cached fallback. draft_digest fails its format check twice → whole run aborts. Fewer than 3 signal sources returned data, or everything traces to one account → abort before grouping. A theme matches two framework clauses at different priorities → that theme goes to Unclear, run continues. Roadmap and capacity note disagree on the same initiative → drop that theme’s committed tag, run continues.

Hard timeout: 300s wall clock. Delivery deadline is 8:00, so nothing shipped by 8:05 aborts and sends the failure line.

Cost ceiling: $1.50 a run, aborts at the next step boundary.

**Structured Tool Outputs** (Tools):

Every tool returns a status and a count. No prose, so Juno never reads a sentence and works out what it means.

read_signals(source, window) — ok: {status:"ok", record_count:14, records:[{id,account,timestamp,body}]} / fail: {status:"unreachable", attempts:2} / {status:"empty", record_count:0}. Empty counts as a failure, not a quiet week — #cs-escalations has never had a zero week, so zero means the query broke.
read_framework() — ok: {status:"ok", clause_count:4, clauses:[...]} / fail: {status:"unreachable"} or {status:"partial", clause_count:2}. Under 4 clauses kills the run.
read_roadmap() — ok: {status:"ok", initiative_count:11, initiatives:[{name,quarter,commitment,owner_pod}]} / fail aborts.
read_capacity_note() — ok: {status:"ok", pods:[{name,blocked,blocked_on}]} / fail aborts.
read_memory() — ok: {status:"ok", theme_count:9, counted_id_count:212} / fail aborts, or it recounts every live thread as new.
group_signals() — {theme_id, signal_ids, customer_count:2, mention_count:2, internal_count:1}. customer_count is computed from distinct accounts in signal_ids; nothing can set it directly.
match_priority() — {priority:"P0", clause_text, match_count:1} / {priority:"unclear", match_count:0} / {priority:"unclear", match_count:2, clauses:[...]}. No path returns a priority with match_count 0.
match_roadmap() — {match:"exact", initiative, commitment} / {match:"none"} → Promised, not built / {match:"conflict", roadmap_says, capacity_says}.
draft_digest() — {status:"pass", gates:{...six booleans}, row_count:4} / {status:"fail", failed_gate, failed_theme}, which is word for word my failure message.
deliver_to_pm() — {status:"sent", message_ts} / {status:"failed", error_code}
write_memory() — {status:"ok", themes_written:4} / {status:"failed"} — digest still went out, but next week recounts, so it tells me the counts are suspect.

**Confidence Thresholds** (Verification):

Per theme. High — two or more distinct customers, exactly one framework clause matched, every quote verbatim, every source resolves. Normal row with its count and priority printed plainly. Medium — one customer only, or roadmap and capacity note disagree, or one signal came from a degraded source. Still a row, but labelled: “single voice, not a pattern,” committed tag dropped, or count marked a floor. Low — zero clauses matched, two at different priorities, a source that won’t resolve, or no verbatim quote. Out of the table, into Unclear with the reason.

Per run. High — all six signal sources ok, ships normally. Medium — one or two degraded, ships with the dead source named and every count marked a floor. Low — under three sources, everything from one account, or a reference doc down. No digest, one line naming the condition.

The rule underneath: a theme can lose confidence and stay visible. What it loses is the number, because the number is the thing I’d act on without checking.

**North Star** (Context):

Show me what customers actually said this week and how many of them said it, with the evidence attached to every number — never decide what we do about it.

Always: attach signal ids to every theme so the count is computed from evidence rather than written beside it; quote verbatim, trimmed to the symptom; cite the framework clause behind every priority and the roadmap initiative behind every committed tag.

Never: invent a customer name, a count, a quote, or a framework clause — if the clause doesn’t cover it, the answer is Unclear. Never rank by business value, propose a fix, or assign an owner. Never write anywhere except my DM and its own memory.

## Rules of Engagement

**Agency Permission:**

Permissions. Same dial — read auto, draft auto, write auto, send blocked — only now expressed as what it decides versus what it hands over, with the DM named as the single checkpoint.

**Access Control:**

comes from PRD §01 Context. The six sources and three reference docs are your source list; the out-of-reach list is your exclusions, with one change that matters: in Module 3 ARR was excluded because you didn’t want it ranking by money. Here it’s enforced by the grant instead of by instruction, which is the thing that makes it a permission rather than a rule.

**Fallback Protocols:**

is PRD §06 Verification plus §03 Loop. The gate failures and the refusal floor come from §06, the retry counts and the timeout from §03.

What Module 4 adds on top of Module 3 is enforceability. The PRD said what should happen. This says what the service account can reach, what the code constant is, and what number fires which abort.

**Checkpoints:**

One real checkpoint, and it’s delivery. Everything Juno produces stops in my DM. If it goes further it’s because I moved it.

Two things come to me and stop there even though I could make a case for automating both. “Promised, not built” never reaches the rep who said it — that’s a correction about a conversation a human had with a customer, and if Juno has it wrong she ends up in an awkward call she didn’t need to have. The other is a roadmap-versus-capacity conflict. Juno flags it but never resolves it, since that’s two of our own documents disagreeing about what we committed to, and somebody should go sort that out.

Nothing inside the loop. If I put a checkpoint mid-run I’d be approving steps I have no way to judge, and I’d rather spend that attention on the output, which I can.
