## Four Levers

**Stop Conditions** (Loop):

max_steps: 12 tool calls. If it hits 12 it ships what it has with "turn limit reached, counts are incomplete" on it. No quiet truncating.

early abort, any one of these:
- same tool fails twice in a row (about 5 min apart) → drop that source, name it in the window line, keep going
- read_framework, read_roadmap or read_capacity_note fails twice → whole run aborts, no cached fallback
- draft_digest fails its format check twice → whole run aborts
- fewer than 3 signal sources came back with data, or everything traces to one account → abort before grouping
- a theme matches two framework clauses at different priorities → that theme goes to Unclear, run continues
- roadmap and capacity note disagree on the same initiative → drop that theme's committed tag, run continues

hard timeout: 300s wall clock. Delivery deadline is 8:00, so if nothing has shipped by 8:05 it aborts and sends the failure line.

cost ceiling: $1.50 a run. Over that, it aborts at the next step boundary.

**Structured Tool Outputs** (Tools):

Every tool hands back a status and a count. No prose, so Juno never has to read a sentence and work out what it means.

**`read_signals(source, window)`**
Works: `{status: "ok", source, window, record_count: 14, records: [{id, account, timestamp, body}]}`
Fails: `{status: "unreachable", source, attempts: 2}`
Zero records: `{status: "empty", record_count: 0}` — and I'm counting empty as a failure, not a quiet week. `#cs-escalations` has never had a zero week, so zero means the query broke or the window is off. It gets named in the window line like any other dead source.

**`read_framework()`**
Works: `{status: "ok", clause_count: 4, clauses: [{level: "P0", includes: [...], excludes: [...]}]}`
Fails: `{status: "unreachable"}` or `{status: "partial", clause_count: 2}`. Under 4 clauses is partial and kills the run, because a half-loaded framework will happily assign priorities from whichever levels did load.

**`read_roadmap()`**
Works: `{status: "ok", initiative_count: 11, initiatives: [{name, quarter, commitment, owner_pod}]}`
Fails: `{status: "unreachable"}`. Run aborts.

**`read_capacity_note()`**
Works: `{status: "ok", pods: [{name, blocked: true, blocked_on: "reporting table sharding"}]}`
Fails: `{status: "unreachable"}`. Run aborts.

**`read_memory()`**
Works: `{status: "ok", theme_count: 9, counted_id_count: 212, carry_forward: [...], promised_open: 2}`
Fails: `{status: "unreachable"}`. Aborts, because without the counted-id ledger it recounts every live thread as new.

**`group_signals(signal_ids, theme_name)`**
Returns `{theme_id, name, signal_ids, customer_count: 2, mention_count: 2, internal_count: 1}`.
`customer_count` is computed from distinct accounts in `signal_ids`. Nothing can set it directly.

**`match_priority(theme_id)`**
Works: `{priority: "P0", clause_text: "...", match_count: 1}`
Nothing matched: `{priority: "unclear", match_count: 0}`
Two clauses, different levels: `{priority: "unclear", match_count: 2, clauses: ["P0 ...", "P2 ..."]}` — goes to Unclear with both printed. There's no path that returns a priority with `match_count: 0`.

**`match_roadmap(theme_id)`**
Works: `{match: "exact", initiative, quarter, commitment}`
Nothing: `{match: "none"}` — which is what lands something in Promised, not built.
Conflict: `{match: "conflict", roadmap_says: "committed Q3", capacity_says: "pod blocked"}` — tag dropped, flagged to me.

**`draft_digest(...)`**
Works: `{status: "pass", gates: {quote_verbatim: true, counts_derived: true, sources_resolve: true, clause_cited: true, roadmap_matched: true, format_ok: true}, row_count: 4}`
Fails: `{status: "fail", failed_gate: "quote_verbatim", failed_theme: "SSO setup fails"}` — which is word for word what goes in my one-line failure message.

**`deliver_to_pm(digest)`**
`{status: "sent", message_ts}` or `{status: "failed", error_code}`

**`write_memory(...)`**
`{status: "ok", themes_written: 4, ids_written: 11}` or `{status: "failed"}`. The digest still went out, but next week will recount, so it tells me the counts are suspect.

**Confidence Thresholds** (Verification):

Per theme

High — normal row in the table. Two or more distinct customers, exactly one framework clause matched, every quote verbatim, every source resolves. This is the only state where a theme gets a count and a priority printed plainly.

Medium — row in the table, but labelled. One of these is true: only one customer raised it, or the roadmap and capacity note disagree on it, or one of its signals came from a source that was degraded this run. It still appears, but it carries the reason — “single voice, not a pattern,” or the committed tag is dropped, or the count is marked a floor. I can act on a medium row, I just can’t treat the number as settled.

Low — doesn’t go in the table. Zero framework clauses matched, or two at different priorities, or a source that won’t resolve, or the only quote isn’t verbatim in any record. It goes to Unclear with the reason attached. This is the one I care most about getting right: low confidence means it loses its count and its priority, not that it disappears.

Per run

High — all six signal sources returned ok. Digest ships normally.

Medium — one or two sources degraded. Digest still ships, window line names the dead source, every count in the run is labelled a floor rather than a total.

Low — fewer than three sources returned data, everything traces to one account, or a reference doc is down. No digest. One line saying which condition fired.

The rule underneath all of it: a theme can lose confidence and still be visible. What it loses is the number, because a number is the thing I’d act on without checking.

**North Star** (Context):

Always

Attach the signal ids to every theme, so the count is computed from the evidence and not written beside it
Quote verbatim, trimmed to the symptom, never reworded
Cite the framework clause behind every priority and the roadmap initiative behind every committed tag

Never

Invent a customer name, a count, a quote, or a framework clause. If the clause doesn’t cover it, the answer is Unclear.
Rank by business value, propose a fix, or assign an owner
Write anywhere except my DM and its own memory

## Rules of Engagement

**Agency Permission:**

Decides alone: which signals group into which theme, what a theme is called, which quote represents it, whether a priority clause matches cleanly, whether a roadmap item matches, whether to refuse the run.

Proposes and waits: the digest itself. It lands in my DM as a draft and goes no further without me.

Cannot decide at all: what we build, what we prioritize, who owns something, whether a theme matters more than another one. Priority comes from the framework and the order comes from the customer count. Where the framework doesn’t settle it, Juno doesn’t either — the theme goes to Unclear.

**Access Control:**

Runs as a service account scoped to exactly six signal sources and three reference docs, not as me. If I get added to a new channel next month, Juno doesn’t see it until someone adds it to the list.

Reachable: #cs-escalations, #support-firehose, #backend-monitoring, the ONB Jira project, the Notion feedback log, the support queue, the CRM call-notes field on Sales-Ops-flagged accounts only, and the three reference docs.

Not reachable, by scope rather than by instruction: ARR and deal-size fields, DMs and private channels, any Jira project but ONB, contract and legal records, anything in the CRM beyond call notes on flagged accounts. These aren’t things Juno is told to ignore. They’re not in the grant, so a prompt can’t talk it into them.

Write scope: my DM, and its own memory store. Nothing else, and the DM channel id is a constant in the code rather than a parameter.

**Fallback Protocols:**

Signal source fails twice → drop it, name it in the window line, mark every count in the run a floor, keep going
Reference doc fails twice → no digest, one line naming the doc
Format check fails twice → no digest, one line naming the gate and the theme
Under three sources, or everything from one account → no digest, lists what it did find
Turn ceiling at 12 → ships labelled “counts are incomplete”
Timeout at 300s, or nothing delivered by 08:05 → abort, failure line
Over $1.50 → abort at the next step boundary
write_memory fails but the digest went out → tells me, because next week will recount

**Checkpoints:**

One hard checkpoint: delivery. Everything Juno produces stops in my DM, and anything that goes further goes because I moved it.

Two things route to me and stop even though I could imagine automating them. “Promised, not built” never reaches the rep who said it — it’s a correction about a conversation a human had with a customer, and if Juno’s wrong she inherits an awkward call she didn’t need. And a roadmap-versus-capacity conflict gets flagged, never resolved. That’s two documents disagreeing about what the company committed to, which is a question for people.

No checkpoint inside the loop. Adding one means I’d be approving steps I can’t evaluate, which is worse than approving the output I can.
